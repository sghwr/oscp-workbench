# Lab7 讲解：虚拟内存

代码在 `code/lab7/`，以 Lab6 为基础修改，提交号是 `fbb4362`。

测试程序是 `code/test/sort.c`，`ARRAYSIZE` 用课程安装包里的值 100，没有改动。每个进程默认分配 5 个帧，置换算法默认用 LRU。

## 1. 整体设计

```
               ┌──────── 交换文件 SWAPn（整个地址空间的映像，第 i 页在偏移 i×128 处）
               │  ▲ 写回脏的牺牲页        │ 读入所需页
               │  │                        ▼
用户访存 → Translate：页表项 valid？ ──否──→ PageFaultException
               │是                             │
               ▼                               ▼
         访问物理内存            ExceptionHandler → space->PageFault(BadVAddr)
                                   ├ 本进程分到的帧 < 5：从 physPageMap 取一个空闲帧
                                   └ 否则：FindVictim() 在本进程自己的帧里选一页（局部置换）
                                            牺牲页是脏页就先写回 SWAPn
                                   读入所需页，设 valid，然后返回，不推进 PC → 重新执行这条指令
```

| 要求 | 实现方式 |
|---|---|
| 纯按需调页 | 构造 AddrSpace 时**一页都不装入**，页表项全部设为 `valid=FALSE`、`physicalPage=-1`，所以第一条取指令就会缺页。代码段和数据段的初始内容，与 bss、栈对应的 0 一起拼成一份映像，写进交换文件 `SWAPn`（n 是 SpaceId） |
| 固定分配（5 帧） | 每个进程最多 `maxFrames` 个帧。`frameOf[slot]` 和 `pageInFrame[slot]` 记录本进程的每个帧以及帧里装着哪一页。可以用 `-mf m` 调整帧数，至少 2 个 |
| 局部置换 | 只在本进程自己的帧中选牺牲页，不会抢别的进程的帧 |
| 置换算法 | 用 `-pra a` 选择，编号和参考程序 n7 一致：1 FIFO、2 二次机会（时钟）、3 增强型二次机会、4 LRU（默认） |
| 统计 | `Statistics` 增加 `numPageWrites`，输出 `Paging: faults X, write backs Y` |
| 交换文件 | 用 Nachos 文件接口（`fileSystem->Create/Open`）读写。Lab7 编译时定义了 `FILESYS_STUB`，所以它实际是宿主机上的文件 `SWAP0`；进程 Exit 时删除。用 Halt 关机时不会删除，参考程序也是这样 |

**四种算法怎么选牺牲页**（`AddrSpace::FindVictim`）：
- **FIFO**：帧按 slot 0、1、2… 的顺序装满，之后也按同样的顺序轮流替换，`hand` 指向的就是进入内存最早的页。
- **二次机会（时钟）**：`hand` 转一圈。遇到 `use=1` 的页，就把 use 清零，跳过它；遇到的第一个 `use=0` 的页就是牺牲页。use 位由 `Translate` 在每次访存时设置，这是 Nachos 模拟的"硬件"做的。
- **增强型二次机会**：按 (use, dirty) 分成四类，优先选 (0,0)：最近没用过、也没修改过，换出时不用写回。
  - 第一圈只找 (0,0)，不修改任何位；
  - 第二圈找 (0,1)，同时把经过的页 use 清零；
  - 如果还没找到，再重复一次，这时一定能找到。
  - 实测它的写回次数最少，只有 196 次，FIFO 是 610 次。
- **LRU**：给 `TranslationEntry` 增加 `lastUse` 字段。`Translate` 每次成功转换地址时写入一个全局的访存计数器 `++referenceClock`，相当于模拟出每页"最后一次被访问的时刻"。选牺牲页时，取 `lastUse` 最小的那页。真实硬件很难在每次访存时都记一个时间戳，这正是 LRU 在实际中代价高的原因。

**三个细节**：
1. **缺页之后不推进 PC**。`OneInstruction` 里 `ReadMem` 或 `WriteMem` 失败时会直接 return，下一轮循环会重新执行同一条指令，这时页已经在内存中了。
2. **内核读用户内存前，先确保页面在内存中**。Exec 的文件名在用户地址空间里，`ReadUserString` 读之前先调用 `MakeResident()` 把页调入，否则内核中的 `ReadMem` 会抛出缺页异常，而这个异常没有用户态的"下一次重试"可言。
3. **为什么至少要 2 个帧**。一条 MIPS 指令可能同时涉及两页：指令本身所在的页，以及它要读写的数据页。只有 1 个帧时，取指令把数据页换出，访问数据又把指令页换出，这条指令永远执行不完。实测 n7 加 `-mf 1` 也会陷入这个死循环，20 秒内输出了 800 多万行。所以我们的 `-mf` 选项强制至少 2 帧。

## 3. 不同置换算法的 user ticks 一样吗？（题 6）

**不一样**，并且有一个精确的规律：

> **user ticks = 331144 + 缺页次数**，所有算法、所有帧数都满足这个式子（见上表）。

331144 是 sort 真正执行完的指令条数，所有算法下都相同，因为程序的逻辑完全一样。多出来的部分正好等于缺页次数，原因在模拟器的主循环里（`machine/mipssim.cc`）：

```cpp
for (;;) {
    OneInstruction(instr);    // 取指令或访存时缺页：ReadMem 返回 FALSE，这里直接 return
    interrupt->OneTick();     // 不管这条指令有没有执行完，都给用户时钟加 1
}
```

每次缺页时，那条指令都"执行了一半就被取消"，但这一次仍然算了 1 个 user tick。缺页处理完以后，这条指令会**重新执行一遍**，又算 1 个 tick。所以每发生一次缺页，就多 1 个 user tick。缺页越多的算法，user ticks 越大。

**另外两点值得写进报告**：
- **Nachos 的 user ticks 并不反映缺页的真实代价**。真实系统中，一次缺页要读磁盘，耗时是毫秒级，相当于几百万条指令的时间，而这里只算 1 个 tick。读写交换文件走的是宿主机的文件（FILESYS_STUB），没有经过模拟磁盘，所以 `Disk I/O: reads 0, writes 0`，也不计入 system ticks。如果要更真实，可以在 PageFault 中按读写一页的磁盘时间（比如 `SeekTime + RotationTime`）手动推进模拟时钟，或者改用 SynchDisk 来读写交换区。
- system ticks 都是 10。整个运行过程中，内核只在用户程序启动时打开过一次中断，缺页处理期间一直是关中断的，不会推进系统时钟。

## 4. 如何在 Nachos 中得到最优置换（OPT）的缺页次数（题 7，只写进报告）

OPT 选择**以后最长时间不会再被访问**的页作为牺牲页，所以必须知道未来的页面访问序列。程序的执行是确定的：同一个程序、同样的输入，访问序列就完全相同。因此可以分**两遍运行**：

### 第 1 遍：记录页面访问序列

1. 在 `Machine::Translate` 中，每次地址转换成功之后，把 `vpn` 追加到一个"访问序列"里。这一点和设置 `lastUse` 的位置相同。
   - **相邻的重复页号可以合并**：连续访问同一页，对 OPT 的决策没有影响，合并后序列会短很多。参考程序 n7 正是这样，sort 的 33 万多次访存只记成了 185772 项。
   - **缺页导致的重试访问不要重复记录**：只在 Translate 返回 `NoException` 时记录。
2. 序列可以存在内存中的动态数组里。更好的办法是写成二进制文件 `REFSTRn`（每项 2 字节或 4 字节），这样第 2 遍运行时可以直接读取。参考程序就是用 `-pra -a` 一边按算法 a 运行、一边记录 REFSTR0。
3. 进程结束时关闭这个文件。

### 第 2 遍：按 OPT 运行，统计缺页次数

1. 启动时把 REFSTRn 整个读入数组 `ref[0..N-1]`，并维护一个游标 `pos`，表示"当前执行到序列的第几项"。每次 Translate 成功（且页号和上一项不同）时 `pos++`，并可以用 `ASSERT(ref[pos] == vpn)` 校验，确认两遍运行的访问序列确实一致。
2. 缺页并且需要换出时，对本进程每个帧中的页 p，求它的下一次访问位置 `next(p)`，即 `pos` 之后 p 第一次出现的下标；如果以后再也不访问，就记为 ∞。选 `next(p)` **最大**的页作为牺牲页。
3. **加速**：每次都向后扫描，最坏要扫完整个序列，代价是 O(N)。可以预先倒着扫一遍，为每一项算出 `nextUse[i]`，即 `ref[i]` 这个页下一次出现的下标，然后为每页维护"当前的下一次使用位置"。这样每次缺页的代价降到 O(帧数)。
4. 其余流程（写回脏页、读入新页、统计 `numPageFaults` 和 `numPageWrites`）和其他算法完全相同。在 `FindVictim` 中增加一个 `case PRA_OPT` 就可以了。

**这样做的结论**：OPT 不能用于真实系统，因为它需要预知未来，但它给出了**缺页次数的下限**，可以用来衡量其他算法离最优还有多远。参考程序的结果是：5 帧下 OPT 缺页 **450** 次，LRU 889 次，FIFO 1377 次，大约分别是最优值的 2 倍和 3 倍。

**一个前提**：两遍运行的访问序列必须完全相同。单个进程的 sort 满足这个条件。如果有多个进程，并且用 `-rs` 随机切换，交错顺序会改变，但每个进程自己的访问序列不会变（局部置换只看自己的序列），所以要按进程分别记录 `REFSTRn`，n 就是 SpaceId。
